# Expected Project Layout: sysml-eagle-netlist-bridge

When using this skill to integrate EAGLE netlist into a SysML project, follow this folder structure:

## Typical Project Organization

```
<project-root>/
│
├── hardware/
│   ├── <design-code>.pl                    # EAGLE parts list (exported from EAGLE)
│   ├── <design-code>.scr                   # EAGLE netlist script (exported from EAGLE)
│   └── <design-code>-ANALYSIS.md           # Human-readable netlist summary (generated by skill)
│
├── sysml-v2-models/
│   └── projects/
│       └── <project-name>/
│           ├── models/
│           │   ├── <hardware-part>.sysml              # Part def (from sysml-hardware-part-generator)
│           │   ├── signals-<design-code>.sysml        # Signal items & connector ports (generated by skill)
│           │   ├── deploy-<project-name>.sysml        # Deployment/wiring (uses connector ports)
│           │   └── config.yaml                        # Load order (includes signals file)
│           │
│           └── outputs/
│               └── system-design-report/
│                   └── interconnection-view.md        # Synced from SysML (optional, via sysml-view-doc-sync)
│
└── README.md                               # Project overview (may reference hardware folder)
```

## File Details

### hardware/ folder

| File | Origin | Purpose |
|------|--------|---------|
| `<design-code>.pl` | Exported from EAGLE | Bill of Materials (parts list) — reference archive |
| `<design-code>.scr` | Exported from EAGLE | Netlist script — complete signal connectivity, reference archive |
| `<design-code>-ANALYSIS.md` | Generated (this skill) | Human-readable summary — power budget, connector pinouts, grounding |

**Example naming:** `86ewy6qck.pl`, `86ewy6qck.scr`, `86ewy6qck-ANALYSIS.md`

### sysml-v2-models/projects/<project>/models/ folder

| File | Origin | Purpose |
|------|--------|---------|
| `<hardware-part>.sysml` | sysml-hardware-part-generator | Logical part def with attributes, high-level ports |
| `signals-<design-code>.sysml` | **This skill (sysml-eagle-netlist-bridge)** | Signal item defs + connector port defs with netlist traceability |
| `deploy-<project>.sysml` | User (deploy architecture) | Uses connector ports from signals file to wire system |
| `config.yaml` | User | Load order: should include signals file after part defs, before deploy |

**Example naming:**
- `pat-breakout-mcu-hat.sysml` (hardware part)
- `signals-86ewy6qck.sysml` (signal consolidation)
- `deploy-leo-cubesat-laser-comm.sysml` (deployment)

### config.yaml model_files order

```yaml
model_files:
  # ... common libs, kernel, ISQ/SI ...
  
  # Project parts (hardware definitions)
  - pat-breakout-mcu-hat.sysml
  - pat-breakout-mcu-hat-cubemx.sysml
  - pat-breakout-polarfire-hat.sysml
  
  # EAGLE netlist consolidation (NEW — this skill)
  - signals-86ewy6qck.sysml
  
  # Deployment (uses signals)
  - deploy-leo-cubesat-laser-comm.sysml
  - behaviour-leo-cubesat-laser-comm.sysml
  - root-leo-cubesat-laser-comm.sysml
```

**Key:** Signals file loads **after** part defs, **before** deploy, so deploy can reference connector ports.

## Multiple Design Versions

If you have **V4, V5, V6** of the same PCB:

### Option 1: Versioned EAGLE files, unified signals
```
hardware/
├── <design-code>-V4.pl
├── <design-code>-V4.scr
├── <design-code>-V4-ANALYSIS.md
├── <design-code>-V5.pl
├── <design-code>-V5.scr
├── <design-code>-V5-ANALYSIS.md
├── <design-code>-V6.pl
├── <design-code>-V6.scr
└── <design-code>-V6-ANALYSIS.md

models/
└── signals-<design-code>.sysml        # References all versions in doc
```

**When to use:** Connectors and signals are **stable** across versions; only netlist details change.

### Option 2: Separate signals per version
```
hardware/
└── (as above)

models/
├── signals-<design-code>-V5.sysml
└── signals-<design-code>-V6.sysml

config.yaml:
  - pat-breakout-mcu-hat.sysml
  - signals-<design-code>-V6.sysml    # Select active version
  - deploy-leo-cubesat-laser-comm.sysml
```

**When to use:** Connectors or major signal groups changed between versions; connector ports must differ.

**Recommendation:** Use **Option 1** unless connectors fundamentally differ.

## Cross-Linking

### In SysML (signals-<design-code>.sysml)
```sysml
doc /*
  Real PCB design (under design): 86ewy6qck (EAGLE v47, 2026-04-06)
  - NUCLEO-H753ZI (U1: STM32H753ZIT6) acquisition MCU
  - AD9837 (U2) for beacon modulation DDS
  
  See hardware/86ewy6qck-ANALYSIS.md for netlist details and signal mapping.
*/
```

### In Analysis doc (hardware/<design-code>-ANALYSIS.md)
```markdown
## SysML Integration

**Corresponding SysML part:** `LeoLaserComm::PatMcuHat` in `pat-breakout-mcu-hat.sysml`

**Signal definitions:** `signals-86ewy6qck.sysml` in `sysml-v2-models/projects/leo-cubesat-laser-comm/models/`

**Connector pinouts:** Defined as `port def` types in signals file; routed in deployment model.
```

### In project README
```markdown
## Hardware

- **Design:** PAT acquisition MCU HAT (86ewy6qck, under design)
- **Files:** See `hardware/86ewy6qck-{ANALYSIS,EAGLE}.md` for netlist and BOM
- **SysML:** See `sysml-v2-models/projects/.../models/pat-breakout-mcu-hat.sysml` for architecture
```

## Validation Checklist

After using this skill:

- [ ] EAGLE `.pl` and `.scr` copied to `hardware/`
- [ ] `<design-code>-ANALYSIS.md` created in `hardware/`
- [ ] `signals-<design-code>.sysml` created in `models/`
- [ ] `config.yaml` updated with signals file in load order
- [ ] `part def` updated with design attributes (code, status, version, date)
- [ ] SysML v2 MCP validates (no errors on signals file + full project)
- [ ] Deploy model wires use connector ports from signals file (e.g., `p1Mcu.spi1`, `jQpd.spi2`)
- [ ] Analysis doc linked in SysML docs
- [ ] Project README cross-references hardware folder and SysML model
